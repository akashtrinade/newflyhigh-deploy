The journey at a glance

Worked example used throughout this doc: expert's rate is ₹1,000/hour, session lasts 60 minutes, and the platform split is 80% expert / 20% TrinaDe of what the client pays.

1 · Client pays Client pays the full session price through Razorpay checkout ₹1,250 charged
2 · Split & hold TrinaDe's ₹250 commission stays; ₹1,000 is the expert's earning — held while the session completes and the settlement window runs ₹1,000 expert · ₹250 TrinaDe
3 · Settlement After the dispute window, checks pass and the earning becomes AVAILABLE in the expert's dashboard Available: ₹1,000
4 · Expert withdraws Expert clicks Withdraw → RazorpayX transfers the money to their bank / UPI automatically ₹1,000 → expert's bank

The money split — 80% expert, 20% TrinaDe

For every payment the split is fixed: 80% of the client's payment goes to the expert's earnings, and 20% stays with TrinaDe as the platform commission.

split formula 
// 60-minute session, expert hourly rate ₹1,000
clientAmount       = ₹1,250                     // what the client pays
expertAmount       = clientAmount × 80%         = ₹1,000
trinaDeCommission  = clientAmount × 20%         = ₹250
Client paysExpert getsTrinaDe keepsSplit
₹1,250 ₹1,000 ₹250 80% / 20%

The split is driven by the commission setting (Admin → Settings → Commission Rate; backend: PricingService — single source of truth). All money math uses BigDecimal with banker's rounding — no floating-point drift.

Step 1 — The client pays

1.1Booking & payment

The client books a session and pays the full client price via Razorpay checkout. Behind the scenes the backend creates a Razorpay order for the exact amount (in paise) and, on successful payment, the money is captured and held — the session's payment status becomes HELD.

1.2Where the money sits

From this moment until the expert is paid, the money is not credited anywhere automatically — the ₹1,000 expert share is held while the session completes and the settlement window runs (so the client can dispute or get a refund inside that window). TrinaDe's ₹250 commission is the platform's share.

Step 2 — Session completes → the earning is created

When the session finishes with status COMPLETED and payment HELD, the backend creates an ExpertEarning record for the expert's share and starts the settlement countdown:

expert_earnings record (MongoDB) 
{
  expertId:            "…",
  interactionId:       "…",          // links to the session
  clientPaidAmount:    1250.00,      // what the client paid
  platformFee:         250.00,       // TrinaDe's share
  expertEarningAmount: 1000.00,      // the expert's share
  status:              "PENDING",    // waiting out the settlement window
  settlementStartTime: 2026-08-21T10:00:00Z,
  settlementEndTime:   2026-08-21T10:10:00Z   // + settlement window
}

The settlement window (the "Dispute Window" in Admin → Settings, default 10 minutes in dev — set it to 24h or longer for production) is the period where the client can dispute or request a refund. Nothing is payable while the earning is PENDING.

Step 3 — Settlement turns PENDING into AVAILABLE

A scheduled worker (every minute in dev) finds PENDING earnings whose window has elapsed and runs five checks. If all pass, the earning becomes AVAILABLE and the amount appears in the expert's Available Balance.

settlement checks — SettlementService 
PENDING → claim → SETTLEMENT_PROCESSING → checks:
 1. Payment is still HELD         (not refunded/voided)
 2. Session is COMPLETED
 3. No active dispute
 4. No refund in progress
 5. No payout already exists for this earning

All pass → status = AVAILABLE   ← now withdrawable
Any fail → revert to PENDING (max 5 attempts, then blocked for admin review)

Disputes and refunds therefore block money from ever becoming withdrawable — a disputed session's earning stays out of the Available Balance until the dispute is resolved.

5.2Bank verification (live mode)

When RazorpayX keys are configured and the expert saves full bank details, the backend creates a contact + fund account at RazorpayX and starts a ₹1 account-validation check. Until the result arrives, the UI shows:

Saved: account ending 6789

⏳ Verifying bank details…

Then the webhook flips it to verified or failed:

Saved: account ending 6789

✓ Bank details verified · Registered name: GAURAV KUMAR

Saved: account ending 6789

A failed verification blocks bank withdrawals until the expert re-saves valid details (UPI-only saves skip verification). In test mode the validation API is unavailable, so this step is skipped and details save directly.

6.2What the backend does, in order
POST /api/expert/payouts/withdraw — ExpertPayoutService.requestWithdrawal 
1. Auth: expert role + bank/UPI details on file
2. Atomically claim every eligible AVAILABLE earning
   (findAndModify: payoutStatus → PROCESSING)  // no double-withdrawal, ever
3. Total < ₹1,000 minimum → release the claims, error out
4. Create Payout (PROCESSING) with the earnings bundle + a
   snapshot of the bank details + idempotency key
5. RazorpayX transfer (automatic mode):
   a. contact  "expert_<id>"         // reuse or create
   b. fund account (bank / VPA)      // from the snapshot
   c. POST /v1/payouts               // IMPS ≤ ₹5L, NEFT above, UPI ≤ ₹1L
      header X-Payout-Idempotency: <payoutId>  // retries can't double-pay
      queue_if_low_balance: true
   d. store gatewayPayoutId + mode on the Payout
6. Respond: "Withdrawal requested" — payout stays PROCESSING
   until the gateway confirms

Any failure inside step 5 (rejected details, gateway down, UPI limit) releases the claims immediately — the payout becomes FAILED with the reason and the full amount returns to Available Balance.

Step 7 — The money lands in the expert's bank

RazorpayX processes the transfer and calls our webhook. payout.processed marks the payout SUCCESS and flips the earnings to PAID (interaction payment status also closes to PAID). The expert's Recent Withdrawals then shows the UTR:

Failure events (payout.reversed / failed / rejected / cancelled) do the opposite: payout FAILED with the reason shown in red, and the earnings are released back to AVAILABLE so the expert can fix their details and withdraw again. If a webhook is ever missed, an hourly reconcile worker re-checks every stuck payout with RazorpayX and applies the same transitions. A processed event arriving after a payout was already failed is never auto-flipped (double-pay protection) — it raises a critical log for manual admin review.

Why the money can't be lost or double-paid

Atomic claims, everywhere

Earnings are claimed with MongoDB findAndModify before any payout is created — two rapid clicks on Withdraw can never pay the same earnings twice. Settlement uses the same pattern.

Gateway idempotency

Every RazorpayX payout is sent with a unique X-Payout-Idempotency key tied to the payout id — if the network drops the response, a retry returns the same payout instead of a second transfer.

Terminal-state guards

Duplicate webhooks and webhook-vs-worker races are no-ops: a SUCCESS payout ignores late failure events, and a FAILED payout is never auto-flipped to SUCCESS.

Failure releases the money

Every failure path (below-minimum, gateway rejection, payout.failed webhook) returns the claimed earnings to AVAILABLE — the expert's balance is never stuck inside a dead payout.

Reconcile worker

If a webhook is missed or the server was down, an hourly worker re-checks every stuck payout with RazorpayX and applies the real gateway outcome.

Snapshot banking

The payout stores the bank details as they were at request time — the expert changing their details mid-flight can't redirect an existing withdrawal.
